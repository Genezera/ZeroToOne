afterpay/sdk-ios/Sources/Afterpay/Helpers/JWT.swift — JWT.decode / CashAppSigningResponse.decodeJwtToken
Raciocínio da revisão
Confirmei os dois defeitos de codigo isoladamente: (1) JWT.decode (JWT.swift:12-15) faz jwt.components(separatedBy: ".")[1] sem checar o tamanho do array -- um jwtToken malformado (ex.: string sem nenhum ponto, ou vazia) causa crash fatal em runtime (index out of range), nao um erro tratavel; (2) a funcao nunca verifica a assinatura (segments[2]) contra nenhuma chave publica -- so faz base64url-decode do payload (segments[1]) e retorna o JSON cru, um anti-padrao classico de manuseio de JWT ('trust without verify'). Rastreei a cadeia de chamada completa: o unico call site de JWT.decode em todo o SDK e CashAppSigningResponse.decodeJwtToken() (CashAppSigningResponse.swift:18), que por sua vez so e chamado dentro de CashAppPayCheckout.signPayment (CashAppPayCheckout.swift:74), que decodifica a resposta HTTP de signToken() -- uma chamada POST feita pelo proprio SDK para cashAppSigningURL, que vem de Configuration.environment (URL fixa controlada pela propria Afterpay/Cash App, sandbox ou producao, nunca fornecida por merchant ou usuario). Ou seja, o unico gerador possivel do jwtToken decodificado e o backend da propria Afterpay -- nao existe nenhum caminho dentro deste repositorio onde um atacante externo (merchant integrador malicioso, usuario final, ou app consumidor) consiga controlar o conteudo desse JWT antes dele chegar em JWT.decode, a menos que quebre TLS (fora do modelo de ameaca padrao de um bug bounty de codigo-fonte). Confirmei tambem, via CashAppSigningResult.swift e o restante de CashAppPayCheckout.swift, que o valor decodificado (amount/redirectUrl/merchantId) e usado so para prefill de UI e log, enquanto a decisao de seguranca real (validar e cobrar o pedido) acontece depois, do lado do servidor da Afterpay, quando o jwtToken original (nao o payload decodificado) e reenviado integralmente de volta via checkoutV3Confirm/cashAppPspInfo.jwt para o backend validar a assinatura antes de finalizar a cobranca -- o client nunca toma nenhuma decisao financeira baseada no payload nao-verificado. Falso positivo por falta de alcancabilidade por atacante real, nao por ausencia do defeito de codigo: a falta de bounds-check (risco de crash se o backend da propria Afterpay um dia devolver um token malformado) e a ausencia de verificacao de assinatura (ma pratica, mesmo que hoje inofensiva) continuam validas como observacoes de qualidade de codigo para o mantenedor, mas nao configuram uma vulnerabilidade exploravel por terceiro dentro do escopo deste SDK.
